# H264 软解码器性能文档

> 测试对象：**TinyH264** 软件 H.264 解码器（Android 2009 swdec 移植，**当前跑 C 分支，pi32v2 汇编未启用**，Baseline profile 专用）
> 测试代码：`lib/video/TinyH264/tinyh264_file_demo.c`（直连解码库，不经 MPI）
> 配套文档：`h264编码性能文档.md`（编码侧，同一批场景源）

---

## 1. 测试目的

为客户提供 BR33 上 H264 软解码在不同**主频 / 内存位置 / 分辨率**下的解码性能（帧率 / 每帧耗时），
用于评估解码能力与资源配置。

> 测试结果请直接跳转到 [**§5.1 汇总表**](#5-性能测试结果)。

## 2. 固定配置（所有组合均不变）

| 配置项 | 值 | 说明 |
|--------|-----|------|
| 解码器 | TinyH264 | Android 2009 swdec 移植版 |
| 汇编优化 | **不启用（跑 C 分支）** | 已实测评估：+3.4%，但**输出 bit 不精确**（cksum 18/18 不一致）+ 间歇性死机 → 不启用。详见 §5.6 |
| 线程数 | **单线程** | `video_1_bsdDecodeInternal` 单次调用只解一个 NAL |
| 输出重排序 | **关闭** | `video_1_bsdInit(storage, 1)`（`noReordering = 1`），每次 `PIC_RDY` 出一帧 |
| 流缓冲 | **2MB 定长 PSRAM** | `TINYH264_STREAM_BUF_SZ`，整文件读入，超长文件截断 |
| 码流来源 | 编码侧 minih264e v2 产出 | 与编码性能文档同一批，配置已冻结（见下） |
| 码流编码配置 | GOP=40 / QP 10~42 / ABR / 单线程 / SIMD 开 | **本次解码测试不改这些**，解码侧不感知码率 |
| 码流码率 | VGA 1000 kbps；QVGA 500 kbps | 由编码侧决定，解码侧仅作记录 |
| 喂狗 | 每次解码调用后 `wdt_clear()` | 单帧最坏 >200ms，不喂会被 16s 看门狗复位 |
| 计时接口 | `timer_get_ms()` | **与编码侧 `mpi_yuv_h264.c` 同接口、同 ms 口径** |
| fps 口径 | 纯解码耗时 | 仅 `video_1_bsdDecodeInternal`，**不含 SD 卡 IO** |

## 3. 测试变量与组合矩阵

### 3.1 性能配置变量

**3 个变量 → 2（主频）× 3（内存）× 2（分辨率）= 12 组**（与编码侧同构）。
汇编优化曾作为第 4 个变量评估，因正确性问题已关闭（§5.6）：

| 变量 | 取值 | 说明 |
|------|------|------|
| ~~汇编优化~~ | ~~关闭 / 开启~~ | **已评估并关闭，不再作为测试变量**（结论见 §5.6）。开关为 `VIDEO_1_BSD_PI32V2_EN`，当前 `= 0` |
| 主频 | **320 MHz / 240 MHz** | CPU 主频（320 MHz 需对应 320M 库/时钟配置） |
| 内存位置 | **PSRAM@200MHz / PSRAM@400MHz / SRAM** | 解码器内存（码表/参考帧/宏块存储）所在内存。<br>⚠️ **PSRAM@400 当前硬件有问题（解码失败），无法测试**，见 §7 |
| 分辨率 | **VGA 640×480 / QVGA 320×240** | 对应编码侧 1000 / 500 kbps 码流 |

> 编码侧测试时汇编优化**恒为开**（`PI32V2_SIMD_EN = 1`），解码侧为**关**（C 分支），
> 两侧汇编口径不同，比较时需注意。

> **SRAM 容量限制（VGA 不可行，见 §5.7）**：VGA 解码器内存需求 **1.13MB**（实测峰值），
> 超出内部 SRAM 可用容量（`TCFG_MMU_MEMORY_SIZE = 1MB`）；且 2MB 流缓冲本身也只能在 PSRAM。
> 故 **VGA + SRAM 不可测**（#5/#11 标 N/A），QVGA + SRAM 才可行（≈0.30MB）。详见 §5.7。

## 4. 测试方法

1. **测试源文件**：`storage/sd1/C/H264/` 下放 17 个 `.264`（Annex-B，Baseline `profile_idc=66`）。
   需按分辨率分别准备：VGA 码流（640×480）、QVGA 码流（320×240），由编码侧同配置产出。
2. demo 逐个文件执行：**一次性读入 2MB PSRAM 缓冲** → 循环 `video_1_bsdDecodeInternal()` 直到缓冲耗尽。
   文件大于 2MB 时截断，并回退到缓冲内最后一个 start code（丢弃尾部不完整的 NAL）。
3. 计时用 **`timer_get_ms()`**（与编码侧 `mpi_yuv_h264.c` 同一接口、同一 ms 口径）包裹
   **单次 `DecodeInternal` 调用**；每次 `PIC_RDY` 输出一帧并累加该帧耗时；
   文件结束打印该文件汇总，全部结束打印全局 `TOTAL` 汇总：
   ```
   [TinyH264] cp1.264: SPS profile_idc=66 level_idc=22 640x480 (mbs 40x30) poc_type=2
   [TinyH264] RESULT cp1.264|cp|fidx=1|frames=304|calls=361|avg=99.7ms|min=..ms|max=..ms|fps=10.0
   [TinyH264] MEM file=cp1.264 decoder_psram_peak=1186638 bytes (1.13MB), stream_buf=2097152 (2.00MB), sum=3.13MB/4MB
   ...
   [TinyH264] TOTAL frames=... calls=... bytes=... decode_ms=... avg=...ms min=...ms max=...ms fps=...
   ```
4. **取每个文件的 `fps`**，按 cp/ey/ot/map 归类，同场景类取均值，填入第 5 节结果表。

### 4.1 统计口径定义

```
avg_ms = 纯解码总耗时(ms) / 输出帧数          （每帧）
fps    = 1000 / avg_ms
min/max_ms = 按帧聚合（同一帧的多次 DecodeInternal 调用累加后取 min/max）
```

### 4.2 数据口径修正说明（重要）

本版测试过程中修正了以下 demo 统计缺陷，引用早期日志数据时需注意：

| # | 原缺陷 | 对 **性能数字** 的影响 |
|---|--------|------|
| 1 | **fps 公式少乘 100**（且 32 位中间量溢出） | **这是早期日志 fps 看着低 100 倍的唯一原因**。日志显示 `fps=0.09`，实际 9.0。`avg_us` 本身一直是对的 |
| 2 | 旧版 256KB 滑窗喂流，`feed_boundary` 定义在循环体内，导致每喂 1 个 NAL 就 refill 一次 | **对 `avg_us`/`fps` 无影响**——refill（memmove + fread）发生在 `t0..t1` 计时窗口**之外**。只影响 demo 的墙上时钟，以及 `offset=` 诊断恒为 0 |
| 3 | min/max 按"每次调用"统计，与 avg（按帧）量纲不一致 | 曾误报 `min=24us`（实为 SPS NAL 耗时），非最慢/最快帧。**avg 不受影响** |
| 4 | "文件读完"时把末个不完整 NAL 也喂入 | 帧数统计少 1 帧（把正常收尾误报成 `decode failed`），影响 fps 分母 |
| 5 | 首个 `PARAM_SET_ERROR` 直接放弃整个文件 | 部分文件恒得 0 帧 |
| 6 | 计时用 `get_system_us()`（µs），与编码侧 `timer_get_ms()` 不一致 | 口径无法直接对照，已统一为 **ms**（§4.3 已验证两口径等价） |

> **结论**：早期日志中 **只有 fps 一列不可用**（差 100 倍）；**`avg_us` 一直有效**，
> 与现在测得的数值同级（见 §4.4）。引用旧数据时把 fps ×100 即可。

> **ms 口径的精度影响**：单帧耗时约 66~120ms，1ms 分辨率对应 ~1% 量化误差，可忽略；
> 但单次 `DecodeInternal` 调用（如 SPS/PPS 小 NAL）会量化为 0ms，
> 故 min/max **必须按帧聚合**后再取，不能按调用取。

### 4.3 计时口径换算与验证（µs → ms）

`avg`（= 总耗时 / 帧数）在两种计时口径下都应一致，差异仅来自 ms 的整数截断。
已用同源固件分别跑 µs 版与 ms 版并逐项对照：

| 项 | 结果 | 性质 |
|--------|------|------|
| 同源固件两次运行（09-14 21:25 vs 09-15 09:25，均 µs） | 14 个文件 avg 逐项偏差 **≤ 0.088%** | 实测：测量可复现 |
| **µs 版 vs ms 版（16 个文件 avg 逐项对照）** | **最大偏差 0.087%**（理论量化上界 0.75%） | **实测：两口径等价** |
| 结论 | ms 与 µs 差异 ≪ 测量噪声，**统一采用 ms 口径**（与编码侧一致） | 已确认 |

> **注意**：`avg` 两口径等价，但 **min/max 只有 ms 版可用**——µs 版的 min/max 按"每次调用"统计，
> 量纲错误（见 §4.2 #3）；ms 版已改为按帧聚合。

### 4.4 测量方法有效性验证（墙上时钟交叉核对）

计时窗口只包住 `video_1_bsdDecodeInternal()`，需确认它确实覆盖了全部解码开销
（即没有把耗时漏在窗口外）。用日志时间戳做独立核对：
`(RESULT 时刻 − SPS 时刻) / 帧数` 应与 `avg` 一致。

| 文件 | 墙上时钟 s | 墙上 ms/帧 | 计时窗口 avg ms | 差 |
|------|-----------:|-----------:|----------------:|---:|
| cp1.264 | 30.25 | 99.5 | 99.7 | −0.19% |
| cp2.264 | 57.42 | 119.4 | 119.4 | −0.02% |
| ey2.264 | 36.53 | 70.3 | 70.3 | −0.07% |
| ey5.264 | 41.53 | 79.7 | 79.7 | +0.01% |
| ot3.264 | 19.06 | 107.7 | 107.7 | +0.00% |
| map1.264 | 40.28 | 66.6 | 66.6 | −0.04% |

> **结论**：两者差 **<0.2%**，即计时窗口基本覆盖了全部解码耗时，
> `avg` 是可信的"纯解码吞吐"，demo 测量方式有效。
> 另：这也说明 2MB 缓冲方案下**没有** refill 类开销混入（§4.2 #2）。

> **备注**
> 1. **单线程结果**：所有数据基于**单线程单核**测得，多线程多核不在本次范围内。
> 2. **N/A 的两种含义**（均非"不支持"）：
>    - **VGA + SRAM（#5/#11）= 不可行**：解码器需 1.13MB > SRAM 1MB，内存超限。详见 §5.7
>    - **PSRAM@400（#3/#4/#9/#10）= 测不了**：当前硬件在 @400 下解码失败。详见 §7

>    因 map 帧数占比不小（VGA 21% / QVGA 25%）且最快，故全局**低于**四列算术平均
>    （如 #6：算术平均 65.4，帧数加权 61.8）。
> 4. **map 场景最快**（各组均高于 cp/ey/ot 约 1.2~1.6 倍）—— 地图画面平坦、宏块跳过率高，
>    与 §6.1 的瓶颈定位一致。注意 map 无编码侧对应源，**不参与 §5.3 的编解码对比**。

>    → 瓶颈在逐宏块的 C 重建流程，不在熵解码。

| 主频 | PSRAM → SRAM 提速 |

### 5.6 汇编优化（PI32V2）评估：不启用

编码侧测试为**开汇编**（`PI32V2_SIMD_EN = 1`），解码侧源码同样内置了 pi32v2 内联汇编
（4×4 IDCT、`fast_clip` 的 `sat8` 等，见 `transform.c` / `util.h`），
由 `VIDEO_1_BSD_PI32V2_EN` 控制（对应编码侧那个宏）。故做了 A/B 对比。

#### 性能对比（240MHz / PSRAM@200 / VGA，17 文件 7868 帧）

| | avg ms | fps | 相对 |
|---|---:|---:|---:|
| 汇编关（C 分支） | 88.1 | **11.4** | — |
| 汇编开 | 85.2 | **11.7** | +3.4% |

逐文件高度一致（2.7%~4.1%，17/17 均为正），**不是噪声**。

#### 正确性对比（YUV 逐帧校验和）

给 demo 加了输出 YUV 的校验和（`cksum`，按帧混淆累加，覆盖全部帧）：

| | 结果 |
|---|---|
| 两次运行帧数 | **完全相同**（7868 帧，逐文件一致） |
| 两次运行像素校验和 | **18/18 全部不一致**（17 个文件 + 全局） |

**结论：开汇编后图像内容错误，且每一帧都有。** H.264 的反变换是 bit-exact 强制的
（标准 8.5.12/8.5.13 规定整数精确运算，不像 MPEG-2 允许 ±1 LSB），
所以同一码流下两版输出必须逐比特相同。差异是系统性的（全帧不同），
不是错误掩盖（concealment）造成的局部差异。

可疑点：`transform.c` 的 `idct4x4_col_simd_shr` 中 `r5`/`r7` 的加载被注释掉
（`# r5 = [%0+8]`），却直接使用 `r5 >>> 1`，读的是寄存器残值；
该分支从未被编译过（首次启用才暴露 2 处 `-Wincompatible-pointer-types` 错误），
作者预留的 `idct4x4_scalar` 对比函数也从未被调用。

#### 其它现象

同一配置（汇编开）三次运行：**2 次正常、1 次卡死**（日志停止、无异常打印）。
属间歇性故障，与读未初始化寄存器（取决于编译器分配/内联布局）的特征一致。

#### 结论

| 项 | 值 |
|---|---|
| 收益 | **+3.4%**（85.2ms vs 88.1ms） |
| 代价 | 输出 bit 不精确（每帧都有误）+ 间歇性死机 |
| 决定 | **不启用**，`VIDEO_1_BSD_PI32V2_EN = 0`，本文档全部数据均为 C 分支 |

收益天花板本就低——该分支只为 4×4 IDCT 写了汇编，**熵解码（CAVLC）、帧内/帧间预测、
亚像素插值、去块滤波全是纯 C**，而这些才是耗时大头（见 §6.1）。
即使修好也只有 ~3%，不值得为此引入死机风险。更划算的方向见 §6.2。

### 5.7 VGA + SRAM 不可行性分析（#5 / #11）

结论：**VGA（640×480）+ SRAM 组合不可行**，非"未测"而是"内存放不下"。
SRAM 组合只有 **QVGA** 才有意义。

#### 内存需求拆解（VGA = 40×30 = 1200 宏块）

| 项 | 大小 | 说明 |
|---|---:|---|
| 宏块存储 `pStorage->mb` | 307 KB | `sizeof(mbStorage_t)` = **256 B** × 1200 宏块 |
| **参考帧缓冲（DPB）** | **461 KB × 帧数** | `picSizeInMbs × 384 + 47`，**每帧 461KB** |
| 宏块层 `mbLayer` | 1.3 KB | `sizeof(macroblockLayer_t)` = 1256 B |
| sliceGroupMap / storage / 参数集等 | ~几个 KB | |
| **解码器合计（实测峰值）** | **1.13 MB** | 日志逐文件打 `decoder_psram_peak=1186638`，与分辨率绑定 |
| 流缓冲 | **2.00 MB** | `TINYH264_STREAM_BUF_SZ`，定长 |

#### 两个超限点

1. **流缓冲 2MB** 完全无法进 SRAM（SRAM 总量仅 1MB）
2. **解码器自身 1.13MB > 1MB** —— 即使流缓冲留在 PSRAM，光解码器也已超限

所以不是"能解多少帧"的问题（那是流缓冲决定的，缩小即可），
而是**第一次分配参考帧就放不下**。

#### 与编码侧对照

| | VGA 内存需求 | SRAM 可用 | 结果 |
|---|---:|---:|---|
| 编码器（minih264e） | 1.72 MB（persist 1.01 + scratch 0.71） | 1 MB | N/A，超 72% |
| **解码器（TinyH264）** | **1.13 MB** | 1 MB | N/A，**超 13%** |

编码侧因同样原因把 #5/#11 标 N/A（见编码文档 §5.1 备注 2），解码侧结论一致。

#### QVGA + SRAM 是可行的

按宏块数（面积）缩放到 1/4：

| | VGA（1200 MB） | QVGA（300 MB） |
|---|---:|---:|
| 宏块存储 | 307 KB | 77 KB |
| 参考帧缓冲（每帧） | 461 KB | 115 KB |
| **解码器合计** | 1.13 MB | **≈ 0.30 MB** |

**≈0.30MB 在 1MB SRAM 内余量充足** —— 这才是 SRAM 组合的有效测试点（#6 / #12），
与编码侧"QVGA+SRAM 可测、VGA+SRAM 不可测"的结论一致。

#### 为什么不用"减少参考帧"来硬塞

DPB 是最大头（461KB/帧），把参考帧数压到 1 帧确实能降到 ≈0.67MB 而塞进 SRAM。但：

- 参考帧不足会让 P/B 帧大量走**错误掩盖（concealment）**，画质崩坏
- 掩盖路径的耗时与实际解码差异很大，**测出来不是这套解码器的真实性能**

故不采用。

## 6. 分析

### 6.1 瓶颈定位

640×480 = 40×30 = **1200 宏块/帧**：

| 分辨率 | 主频 | 内存 | 全局单帧 | us/MB | **cycles/MB** |
|---|---|---:|---|---:|---:|---:|
| VGA (1200 MB) | 240MHz | PSRAM | 88.1ms | 73.4 | **17,600** |
| VGA (1200 MB) | 320MHz | PSRAM | 71.4ms | 59.5 | **19,000** |
| QVGA (300 MB) | 240MHz | PSRAM | 24.8ms | 82.7 | **19,800** |
| QVGA (300 MB) | 320MHz | PSRAM | 19.8ms | 66.0 | **21,100** |
| QVGA (300 MB) | 240MHz | SRAM | 21.6ms | 72.0 | **17,300** |
| **QVGA (300 MB)** | **320MHz** | **SRAM** | **16.2ms** | **54.0** | **17,300** |

- **同分辨率下两档主频的 cycles/MB 接近**（差 8% / 6%），即 §5.2.2、§5.2.4 的主频效率 92.6% / 93.9%
- **QVGA 的 cycles/MB 比 VGA 高约 12%** —— 小分辨率下固定开销占比更大
  （每帧的 SPS/PPS 处理、DPB 管理、函数调用开销被更少的宏块摊薄）
- **换 SRAM 后 cycles/MB 降到与 VGA 同档**（17,300 vs 17,600），且**两档主频完全相同**——
  访存延迟被消除后，单位计算量回到"纯计算"水平（这正是 SRAM 下主频效率 99.9% 的来源）

每宏块约 1.7~2.1 万周期。这是**未启用 SIMD 优化的 C 实现**的典型量级
（DSP 上优化的 H.264 解码器通常在 500~2000 cycles/MB）。
说明耗时集中在**逐宏块的预测 + 变换 + 重建 + 去块滤波**，而非码流解析。

`map1.264` 的佐证：字节/帧只有 2111（远比其他文件的 ~4700 小），单帧耗时也最短（66.6ms），
两者同向变化 → 码流越短、跳过宏块越多、逐宏块处理越少，耗时越低。

#### ⚠️ 关于"是否受 PSRAM 带宽限制"的结论修正

**早期结论（基于主频线性，已作废）**：主频 240→320MHz 效率达 92.6~93.9%，
曾据此推断"解码不受 PSRAM 带宽限制、是纯 CPU 计算瓶颈"。

**修正后的结论（基于 SRAM 实测）**：该推断**不成立**。
§5.2.5 实测 **PSRAM → SRAM 提速 22.2%**，说明解码**明显受内存子系统影响**。

正确的表述是：

| 观察 | 正确解读 |
|---|---|
| PSRAM 下 240→320MHz 效率 92~94% | 这一档**没有触及内存瓶颈**，**不等于**访存不敏感 |
| PSRAM → SRAM 提速 **14.9%(240M) / 22.2%(320M)** | 解码对**访存延迟**高度敏感（约为编码侧的 4~6 倍） |
| **SRAM 下 240→320MHz 效率 99.9%** | **决定性证据**：去掉 PSRAM 后主频提升完全线性，说明 PSRAM 下那 6% 损耗正是访存瓶颈 |

**SRAM 收益随主频升高而增大**（240M +14.9% → 320M +22.2%）：
主频提升使**计算时间按 1.333x 缩短**，而**访存延迟（以周期计）几乎不变**
（PSRAM 时钟未变）→ 访存占比升高 → 换 SRAM 的收益变大。

**物理原因**：H.264 解码的运动补偿需按**运动矢量随机读取参考帧**，
这种非顺序访问模式对内存延迟极其敏感；而编码的访存更接近顺序流式，
所以编码侧换 SRAM 只快 3.7%。这也解释了 §5.2.5 中
"map（跳过宏块多、访存占比高）收益 1.33x 而 cp（计算密集）仅 1.17x"的梯度。

**对产品配置的意义**：若追求高帧率，**优先保证解码器内存在 SRAM**，
其收益（+22%）远大于提主频（+23.5% 需 320M，但功耗上升）。

### 6.2 可选的提速方向

| 方向 | 预期收益 | 代价 / 风险 |
|---|---|---|
| **解码器内存 PSRAM → SRAM** | **实测 1.149x(240M) / 1.222x(320M)** | **推荐优先**：收益与提主频相当甚至更高，且不动主频、不增功耗。**仅 QVGA 可行**（VGA 需 1.13MB > SRAM 1MB，§5.7） |
| **主频 240M → 320M** | **实测 1.252x(PSRAM) / 1.332x(SRAM)** | 已实测，见 §5.2.2 / §5.2.4 / §5.2.6。功耗上升，需评估 |
| **SRAM + 320MHz 组合** | **实测 61.8 fps**（QVGA 全局，较 240M+PSRAM 的 40.4 fps **+53%**） | 两者叠加，是本次测试的最优组合 |
| **编译选项 `-Oz` → `-O2`（仅 TinyH264）** | 估计 1.3~1.8x | **尚未实测**（§7 ②）。需单独给该模块加 flag 并确认在 `-flto` 下生效；代码体积增大。不碰算法、零正确性风险 |
| ~~启用 pi32v2 汇编~~ | ~~+3.4%~~ | **已评估否决**（§5.6）：bit 不精确 + 间歇死机，且只为 IDCT 写了汇编，天花板低 |
| 自行补全 SIMD（熵解码/预测/滤波） | 估计 2~4x | 工作量大，需 pi32v2 指令级适配 + bit-exact 验证 |
| 降分辨率（640×480 → 320×240） | 约 4x（宏块数 1/4） | 画质损失，需产品确认 |
| 跳帧解码（只解 I 帧 / 隔帧解） | 与跳帧率成正比 | 只适合缩略图 / 快速预览场景 |

## 8. 复现步骤（每组配置操作）

每组配置需在**编译/烧录前**按需修改下列位置，编译烧录运行 demo，取 5.1 表数据。

| 变量 | 修改位置 | 说明 |
|------|----------|------|
| **分辨率** | 换 SD 卡上 `storage/sd1/C/H264/` 的 `.264` 码流 | VGA / QVGA 两批，按分辨率整批替换 |
| **内存位置** | demo 宏 `TINYH264_DECODER_IN_SRAM`（见下） | `0`=PSRAM（`malloc_psram`），`1`=SRAM（`malloc`） |
| **主频** | 工程/时钟配置 | 240M / 320M |
| PSRAM 频率 | PSRAM 初始化/总线时钟配置 | 200 / 400 MHz（⚠️ @400 当前硬件受阻，见 §7） |

### demo 侧开关（`lib/video/TinyH264/tinyh264_file_demo.c`）

```c
/* ---- 内存位置：0 = PSRAM，1 = 内部 SRAM ---- */
#ifndef TINYH264_DECODER_IN_SRAM
#define TINYH264_DECODER_IN_SRAM   0    /* 测 SRAM 组合改为 1 */
#endif

/* 只切解码器内存（经 ALLOCATE → tinyh264_malloc）。
 * 2MB 流缓冲不受影响，始终在 PSRAM —— 它超过 SRAM 总量，且这正是 §5.7 的组合定义。 */

/* ---- 流缓冲大小 ---- */
#define TINYH264_STREAM_BUF_SZ  (2 * 1024 * 1024)
```

**烧录后先核对 `MEM` 行**，确认内存位置生效：

```
[TinyH264] MEM file=cp1.264 decoder=SRAM decoder_psram_peak=0 ...
                              ^^^^^^^^^^^^                    ^
                              PSRAM 或 SRAM                     SRAM 时应为 0
```

### 开启 demo

`apps/watch/app_main.c`：

```c
extern void tinyh264_file_demo(void);
tinyh264_file_demo();
```

编译烧录：`make`，产物 `cpu/br33/tools/app.bin`。

## 附 A：High profile 码流转 Baseline 的命令

只改 SPS 的 `profile_idc` 字节**不够**：High 工具集（CABAC / 8x8 transform / weighted pred）
会让解码器在 PPS 或宏块层失败，必须真正重编码：

```bash
ffmpeg -i in.264 -c:v libx264 -profile:v baseline -level 3.1 -pix_fmt yuv420p \
       -x264-params cabac=0:ref=1:8x8dct=0:weightp=0:bframes=0 out_baseline.264
```

> 本文档 §5.2 的 `map1.264` / `map2.264` 即按此转换（原为 `profile_idc=100`，转换后为 66）。

## 附 B：解码器能力边界

TinyH264 为 **Baseline profile 专用**。遇到 High/Main profile 码流会直接失败（0 帧），
典型报错：

| 码流特征 | 报错 |
|---|---|
| High profile（`profile_idc=100`，SPS 含 chroma_format_idc 等字段） | `ERROR: frame_mbs_only_flag` |
| CABAC（`entropy_coding_mode_flag=1`） | `ERROR: entropy_coding_mode_flag` |

因此**码流必须由 Baseline 配置产出**（编码侧 `minih264e` 写死 `profile_idc=66`，天然兼容）。
